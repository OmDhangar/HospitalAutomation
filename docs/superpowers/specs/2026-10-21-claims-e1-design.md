## 3. Core Architectural Principles & Invariants

1. **Claims Never Block Patient Discharge:**
   - Inpatient clinical care and discharge must never be held hostage by administrative insurance processing.
   - The module `enforce` stage provides visual warnings and billing split reconciliation alerts; it **never** prevents patient physical discharge or doctor sign-off.
2. **Platform Payer Master vs. Tenant Overrides:**
   - Platform payer master (`payer_profiles`) contains standardized IRDAI codes and portal links, editable exclusively by platform administrators.
   - Tenant-specific rules (custom SLA minutes, required document checklists, local TPA phone numbers) reside in a separate tenant-isolated table (`hospital_payer_configs`).
3. **Multiple Claim Cases per Admission:**
   - A single patient admission may have multiple associated claims (e.g., Primary Employer Corporate Cover + Secondary Personal Health Top-up, or Split Insurer Billing).
   - Each claim references an `encounter_payers` record via `encounter_payer_id`.
4. **Decoupled Creation via Domain Events:**
   - Claims are not generated by mutating core billing routines (`setPayerInTx`).
   - Instead, recording a non-self payer emits a domain event / explicit service action (`createClaimCase`), allowing asynchronous or manual curation from the TPA desk.
5. **No Ad-Hoc File Uploads:**
   - Pending an enterprise object-storage infrastructure, Phase E1 does not introduce a custom file-upload subsystem.
   - In-system artifacts (discharge summaries, finalized bills, lab orders) are linked by foreign ID. Physical documents (Aadhaar cards, signed claim forms, insurance cards) are tracked via a tamper-evident "paper filed" physical custody checklist.
6. **Privacy-Safe Alerts:**
   - All background worker alerts and UI notifications are strictly aggregate counts. No patient names, MRNs, bed labels, or payer names appear in alert banners.

## 4. Security, Cryptography & Compliance

### 4.1 Field-Level Authenticated Encryption (AES-256-GCM)
Both `policy_number` and `member_id` represent sensitive financial health identifiers subject to statutory privacy safeguards:
- **Dedicated Key Management:** Uses `CLAIMS_ENCRYPTION_KEY` exclusively. The service **fails closed** if this environment variable is missing (no fallback to WhatsApp or platform keys).
- **Authenticated Additional Data (AAD):** Ciphertexts are cryptographically bound to the claim case ID (`claim_cases.id` as AAD buffer). This prevents ciphertext transplantation attacks across different patient claim records.
- **Envelope Storage:** Stored as:
  - `policy_number_ciphertext`, `policy_number_iv` (12 bytes), `policy_number_tag` (16 bytes), `policy_number_key_version` (smallint).
  - `member_id_ciphertext`, `member_id_iv`, `member_id_tag`, `member_id_key_version`.
- **Search & Display via Blind Index & Masking:**
  - Fast UI display uses masked columns: `policy_number_masked` (e.g., `•••• •••• 4921`) and `member_id_masked`.
  - Exact search uses a keyed HMAC-SHA256 blind index (`policy_number_bidx`, `member_id_bidx`) computed using `CLAIMS_BLIND_INDEX_SALT`. The database never searches plaintext or unkeyed hashes.
- **Key Rotation Protocol:**
  - Supports versioned keys (`CLAIMS_ENCRYPTION_KEY_V1`, `_V2`).
  - Re-encryption worker iterates through claims matching `key_version < CURRENT_VERSION` and re-encrypts rows without downtime.

### 4.2 Forensic Auditing & Access Control
- **Decryption Audit & Rate Limiting:**
  - Decrypting a policy number or member ID is gated by `claims.edit` or `claims.admin` and explicitly logs an entry in `record_access_logs` (`action: 'decrypt_claim_identifier'`).
  - Individual users are rate-limited to 10 decryption actions per minute to prevent mass automated exfiltration.
- **Evidence Log (`acct_events`):**
  - Major lifecycle events (pre-auth submission, approval with amount, query dispatch, final settlement, and rejection) generate append-only entries in `acct_events`.
- **Append-Only Event Ledger:**
  - `claim_events` has no cascade delete (`onDelete: 'restrict'`). Voiding a claim case retains historical event records for forensic accountability.

## 6. State Machine & Transition Rules

### 6.1 Cashless Claim Path
```
[ DRAFT ]
   │
   ├─► Action: markPreauthSubmitted (sent_at, channel, ref)
   ▼
[ PREAUTH_SUBMITTED ] ◄──────────────┐
   │                                 │ (Action: markQueryReplied)
   ├─► Query Arrived                 │
   │   └─► [ QUERY_RAISED ] ─────────┘
   │
   ├─► [ PREAUTH_REJECTED ] ──► (Post-Rejection Workflow §6.3)
   │
   ├─► Action: recordPreauthApproved (amount_paise, approval_date)
   ▼
[ PREAUTH_APPROVED ] ◄───────────────┐
   │                                 │
   ├─► Action: requestEnhancement    │
   │   └─► [ ENHANCEMENT_REQUESTED ] ┘
   │
   ├─► Action: markClaimReady (Checklist & Bill Verified)
   ▼
[ CLAIM_READY ]
   │
   ├─► Action: markFinalSubmitted (sent_at, channel, ref)
   ▼
[ FINAL_SUBMITTED ]
   │
   ├─► Action: recordSettlement (settled_amount, deductions, co-pay)
   ├─► [ SETTLED ] (Terminal: Immutable)
   ├─► [ PARTIALLY_SETTLED ] (Terminal: Immutable)
   └─► [ CLAIM_REJECTED ] ──► (Post-Rejection Workflow §6.3)
```

### 6.2 Reimbursement Claim Path
```
[ REIMBURSEMENT_DRAFT ]
   │
   ▼
[ REIMBURSEMENT_DOCS_GATHERING ]
   │ (Checklist completed, doctor summary signed, final bill receipted)
   ▼
[ REIMBURSEMENT_DOSSIER_READY ]
   │
   ├─► Action: markDossierHandedToPatient (patient/kin signature recorded)
   ▼
[ DOSSIER_HANDED_TO_PATIENT ]
```

### 6.3 Post-Rejection & Appeal Workflow
When a claim transitions into `preauth_rejected` or `claim_rejected`:
1. **Option A — Appeal:** Desk initiates appeal (`appeal_in_progress`). Upon submission, transitions to `appeal_submitted`.
   - If won ➔ Transitions to `preauth_approved` (if at pre-auth stage) or `settled` (if at final claim stage).
   - If lost ➔ Transitions to `appeal_lost`.
2. **Option B — Convert to Self-Pay:** Desk marks claim as `closed_cancelled` (reason: `switched_to_self_pay`). Patient account flips to self-settlement on the discharge bill.

### 6.4 Invariants & Guards
- **Settlement Immutability:** Once a claim is in `settled` or `partially_settled`, it is **terminal**. It cannot be cancelled, reverted, or voided.
- **Optimistic Locking:** Every state mutation requires matching `version`. The update statement increments `version = version + 1`. If `version` does not match, the service aborts with `StaleClaimVersionError`.
- **Explicit Mark-as-Sent:** Status never automatically jumps to `preauth_submitted` or `final_submitted`. A user must trigger an explicit action that captures `sent_at`, `channel`, and `reference`.

## 7. Operational Clocks & SLA Definitions

All SLAs are calculated and stored in **minutes**, evaluated by the background worker:

| Clock Name | Trigger Event | Stop Event | Default SLA | Escalation Rule |
|---|---|---|---|---|
| **Clock 1: Initial Pre-Auth SLA** | `preauth_submitted_at` | `preauth_approved_at`, `query_received_at`, or `preauth_rejected_at` | 360 min (6h) | Amber alert at 240m; Red alert at 360m |
| **Clock 2: Active Query Response SLA** | Query `received_at` | Query `replied_at` (during active stay) | 120 min (2h) | Amber alert at 60m; Red alert at 120m |
| **Clock 3: Post-Discharge Query SLA** | Query `received_at` | Query `replied_at` (post discharge) | 1440 min (24h) | Amber alert at 720m; Red alert at 1440m |
| **Clock 4: Final Packet Dispatch SLA** | `admissions.discharge_ready_at` | `final_submitted_at` | 240 min (4h) | Amber alert at 180m; Red alert at 240m |
| **Clock 5: Final Settlement SLA** | `final_submitted_at` | `settled_at` | 43,200 min (30d) | Summary report on overdue settlements |

### 7.1 Background Worker Implementation (`lib/services/sweeps.ts`)
The 5-minute heartbeat worker sweeps open claims:
1. Identifies queries where `status = 'pending_hospital'` and `sla_deadline_at < NOW() + INTERVAL '60 minutes'`.
2. Identifies pre-auths where `status = 'preauth_submitted'` and `preauth_sla_deadline < NOW()`.
3. **Privacy Rule:** Sweeps generate generic notification counts only.
   - Example notification message: *"3 TPA queries require response within 60 minutes."*
   - Strictly **zero** patient names, bed labels, or payer names in notification bodies or banners.

## 8. Role-Based Permissions & Nurse Access Boundary

### 8.1 Permission Matrix (`lib/domain/permissions.ts`)

```ts
'claims.edit': ['owner', 'receptionist'],

```

### 8.2 Scope & Clinical Masking Rules
- **TPA Desk / Receptionist (`claims.edit`):** Full operational access to mutate claim statuses, record pre-authorizations, log queries and replies, and verify paper document custody.
- **Doctor (`claims.view`, `claims.packet`):** Can view claim status, read query descriptions requiring medical justification, and generate clinical claim packets.
- **Nurse (`claims.view` — Status-Only Clinical View):**
  - Inpatient nurses frequently need to know whether a patient is Cashless or Self-Pay to coordinate pharmacy and discharge preparation.
  - **Financial Strip Rule:** When an actor with role `nurse` views a claim, all financial fields (`preauth_amount_paise`, `approved_amount_paise`, `claimed_amount_paise`, `settled_amount_paise`, `co_pay_amount_paise`, `deduction_amount_paise`) are completely omitted or set to `null` by the server service layer. Nurses see only `status`, `payer_name`, and clinical document requirements.

## 11. Verification & Test Plan

### 11.1 Cryptography & Key Management Tests (`lib/security/__tests__/claims-encryption.test.ts`)
1. **Roundtrip Encryption:** Encrypt `policy_number` and `member_id` with AES-256-GCM; verify successful decryption matches original plaintext.
2. **AAD Mismatch Protection:** Tampering with the bound `claim_case_id` during decryption throws an authentication error (`Unsupported state or unable to authenticate data`).
3. **Fail-Closed Key Isolation:** Unsetting `CLAIMS_ENCRYPTION_KEY` causes the service to throw `ClaimsKeyConfigurationError` immediately. It does not attempt fallback to WhatsApp keys.
4. **Blind Index Determinism:** Verifies HMAC-SHA256 blind indexing generates deterministic search tokens without revealing raw identifiers.
5. **Masking Generation:** Asserts strings with varying lengths produce standard 4-character masked outputs.

### 11.2 Domain State Machine Tests (`lib/domain/__tests__/claims.test.ts`)
1. **Valid Path Traversal:** Test transition sequences:
   - Cashless: `draft` ➔ `preauth_submitted` ➔ `preauth_approved` ➔ `claim_ready` ➔ `final_submitted` ➔ `settled`.
   - Reimbursement: `reimbursement_draft` ➔ `reimbursement_docs_gathering` ➔ `reimbursement_dossier_ready` ➔ `dossier_handed_to_patient`.
2. **Illegal State Hops:** Verify that jumping from `draft` directly to `settled`, or from `preauth_rejected` directly to `final_submitted`, throws `InvalidClaimStateTransitionError`.
3. **Optimistic Locking Guard:** Concurrent update attempts passing an outdated `version` number throw `StaleClaimVersionError`.
4. **Terminal State Invariant:** Attempting to void or cancel a `settled` claim throws `ImmutableSettledClaimError`.
5. **Mark-as-Sent Requirement:** Attempting to transition to `preauth_submitted` or `final_submitted` without explicit `sent_at`, `channel`, and `reference` throws a validation error.

### 11.3 Database Security & Multi-Tenancy Tests (`lib/services/__tests__/claims.integration.test.ts`)
1. **Tenant Isolation:** Hospital A cannot select, update, or count claims belonging to Hospital B under PostgreSQL RLS.
2. **Composite FK Enforcement:** Inserting a claim referencing an `admission_id` from another hospital fails with a foreign key violation.
3. **Append-Only Immutability:** Deleting a `claim_cases` record with existing `claim_events` throws a foreign key restriction violation (`onDelete: 'restrict'`).
4. **Non-Negative Money Checks:** Attempting to insert negative values into `preauth_amount_paise` or `settled_amount_paise` violates database check constraints.
5. **Decryption Rate Limiting & Access Logging:** Exceeding 10 policy decryptions in 60 seconds triggers a rate-limit error and writes `record_access_logs`.
6. **Nurse View Financial Stripping:** Verifies that a user with role `nurse` querying claim details receives `null` for all financial amount fields.

### 11.4 Sweeps & Alert Notification Tests (`lib/services/__tests__/claims-sweeps.integration.test.ts`)
1. **Query SLA Alert Generation:** A claim query with deadline 45 minutes in the future generates a warning alert.
2. **Privacy Assertions:** Asserts that generated alerts contain no patient names, bed numbers, or payer names (message body matches regex for generic aggregate count).

### 11.5 CSV Import Tests (`lib/services/__tests__/claims-import.test.ts`)
1. **Size Cap & Row Limit:** Uploading a CSV exceeding 2 MB or 500 rows fails with an explicit limit error.
2. **Strict Identity Matching:** Rows with only phone numbers fail validation. Rows matching exact `ipd_number` and patient name succeed.
3. **Dry-Run Purity:** Dry-run execution generates a structured error report and writes 0 rows to the database.
4. **Idempotent Re-Import:** Re-running an identical CSV batch does not produce duplicate claim records.
